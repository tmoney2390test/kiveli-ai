# World Pulse 2.0 rollout

World Pulse V2 uses global, immutable event occurrences. `together_world_pulse_templates` holds authored source material; a reserved occurrence snapshots public copy, facts, and ordered participant perspectives. Engagements and conversation links are owner/Life scoped. V1 tables and functions remain unchanged for rollback and for non-Pulse dependencies.

The additive migrations create service-only global tables and owner-readable personal tables, enforce unique UTC slots and a 720-hour exclusion per `(world_id, repeat_identity)`, install a transactional world-level scheduler, restrict locations to active canonical places, and cover foreign-key lookups. A fixed 30-day budget has 15 six-event days, 10 seven-event days, and 5 eight-event days, consuming 200 stable catalog ranks. Each rank publishes at the same UTC slot every 30 days; disabling a template leaves a gap rather than shifting other ranks. Spare ranks beyond 199 may fill a damaged slot. Shortages are recorded as degraded; no old event is redated.

The service-only SQL settings row is the authoritative per-world rollout switch. A world with no row or `enabled=false` stays on V1. The optional `KIVELLE_WORLD_PULSE_V2_ENABLED=false` is an emergency global stop; the absent environment secret does not consume one of Supabase's limited secret slots. This allows an Eos-only release: worlds without a validated catalog continue on V1. Enable each world only after its checked-in pack has 200 editorially reviewed templates, `pnpm world-pulse:validate -- --world <slug> --report` passes, the SQL seed is inspected and applied, the 60-day reservations are audited, and the Edge Functions/web client have been validated. The `world-pulse:seed` command creates reviewable SQL; it does not write to a database. The import resolves canonical slugs at execution time and preserves repeat identities and scheduling ranks. A separate, controlled step may refresh copy in future reserved occurrences; identity and publication times cannot change.

To roll back Eos, set its `together_world_pulse_settings.enabled=false`; the next request uses V1. For an emergency global stop, set `KIVELLE_WORLD_PULSE_V2_ENABLED=false` if a secret slot is available. Do not delete V2 tables or linked conversations. Existing chat transcripts remain available through the normal conversation paths. Future V2 reservations can remain stored and invisible; re-enabling requires a fresh catalog and schedule audit. V1 Home/Explore behavior returns with the world disabled.

The scheduler's service-role cron jobs reserve 60 days ahead daily and publish due slots every 15 minutes. The feed has a bounded two-day recovery path when no fresh events exist. Reads only expose published occurrences in the server's preceding 24 hours. Detail opens and new handoffs enforce the same window; existing linked chats continue with bounded seven-day explicit grounding and normal long-term transcript/memory behavior.

Production release gate: keep each unverified world disabled. The server flag alone never enables V2 for a world. The Eos source is `content/world-pulse/eos-meridian-source.mjs`; rebuild its checked-in JSON with `node scripts/build-eos-world-pulse.mjs`, then run scoped validation. All eight published-world packs now pass global content and schedule validation; that does not replace database, editorial, and live handoff checks. Production migrations and content can be staged with a world disabled; enabling it requires a successful catalog-readiness check, reservation audit, and deployed server/client handoffs. Native builds require a separate release and manual device verification.

The four additive migrations were applied to project `mfysnlghlhxxcwnwpxog`. The Eos pack has 200 active templates, 200 distinct repeat identities, ranks 0–199, and all 47 active residents. A live 60-day reservation made 400 occurrences across 30/20/10 six/seven/eight-event days, with zero shortages and a 720-hour minimum repeat; the first due occurrence published successfully. Eos is enabled in the service-only world settings. The other seven published worlds retain V1.

The eight affected Edge Functions and the production web export were deployed. The deployed web asset uses the `https://kivelli.app/supabase` gateway and real publishable key; `kivelli.app` returned HTTP 200, and an unauthenticated Pulse request returned HTTP 401. The web performance budget currently reports 1.06 MiB compressed initial JavaScript against 1.05 MiB and a pre-existing 3.16 MiB startup image against 2.25 MiB; this did not block the release. Authenticated, physical-device handoffs remain to be checked in the live client; no native build was made for this release.

## All-world authored expansion, 2 October 2026

All eight published worlds have 200 checked-in routine incidents and 15 major incidents. Routine events validate resident coverage, one-to-four participant distribution, and a 90-day schedule with six to eight daily publications and no repeat inside 720 hours. Major incidents use an independent ten-week rotation with one or two publications each week, at least three days apart, and a 70-day interval before an identity returns. Major cards have a distinct red border. Residents can recall the last four public major reports in their own world, plus up to three incidents in which they were involved, without receiving other witnesses' private perspectives.

Juniper City's 15 major incidents are now in the seedable catalog alongside its 200 routine incidents. No all-world content import or feature enablement was performed as part of this expansion. Generated seed SQL is review output until applied as a migration. Edge typechecking and database tests remain release blockers in this workspace: the Edge checker receives an access-denied error, and `supabase test db` cannot connect because the local Postgres service is not running. Repeat those checks and validate live roster/place references before enabling additional worlds.
